# Plan: full TypeScript Language Service integration for `.efx`

Status: **Phase 1-4 complete**. The plugin delivers diagnostics, hover, inlay
hints, go-to-definition, find-references, and document highlights inside `.efx`
files. Phase 5 (polish: rename, code actions) remains as future work.

## Implementation notes (what shipped)

We use Volar's language plugin framework for the core virtual-file handling,
with a custom proxy wrapper for definition path rewriting:

1. **Volar language plugin**: Handles file discovery (`extraFileExtensions`),
   content transformation (`.efx` → compiled TypeScript), and position mapping
   via Volar's `Mapping` format. The mappings are derived from Babel's source
   map output.

2. **CodeInformation for different regions** (following Vue's patterns):
   - JSX punctuation (`<`, `>`, `/`): `semantic: false`, `navigation: false`
     to prevent spurious highlights when cursor is on brackets
   - h() call regions: `semantic: { shouldHighlight: () => false }` to
     suppress document highlights while keeping hover
   - Normal code: full semantic features

3. **Inlay hints filtering**: Filters out h() parameter hints (`_tag`,
   `_props`, `_children`) by checking the `displayParts` property (newer TS
   versions use this instead of `text`).

4. **Go-to-definition and find-references**: A proxy wrapper intercepts
   definition and reference methods to:
   - Filter out h.ts definitions (runtime internals)
   - Rewrite `.ts` paths to `.efx` for generated files
   - Convert byte offsets using the source map (accounting for the
     `// @generated` header in disk `.ts` files)
   - Deduplicate references across symbols

5. **Document highlights with JSX tag matching**: Custom handler provides:
   - Tag pair matching: cursor on `<div>` highlights matching `</div>`
   - Only highlights tag names, not full tags with attributes
   - Returns no highlights for whitespace to avoid spurious matches

6. **Dual-file setup**: For module resolution, pre-compiled `.ts` files exist
   on disk (generated by `efx:compile`). TypeScript resolves imports to these
   files. The plugin converts definition results back to `.efx` sources with
   correct positions.

Verified via test harness:
- 0 semantic/syntactic errors in `.efx` files
- Hover shows correct types (e.g., `AtomRef<number>`)
- No h() parameter hints (tag/props/children)
- Go-to-definition on imports and JSX usage points to `.efx` sources at
  correct line/column
- Find-references returns references in `.efx` files with correct positions
- Document highlights show matching JSX tag pairs

## Original analysis (retained for reference)

## 1. Why Layer 1 didn't work

The intent of `@efx/ts-plugin` was: wrap the LanguageService, intercept
reads of `.efx` files, return compiled (non-JSX) content to tsserver,
remap diagnostic positions via the source map. Smoke test passes; in
Neovim the plugin appears to do nothing — tsserver still type-checks
raw JSX in `.efx` files and surfaces `JSX.IntrinsicElements` /
`react/jsx-runtime` errors.

Root cause is upstream of the plugin:

1. **tsserver filters files by extension at project construction.** The
   include glob in `apps/demo/tsconfig.json` is expanded against TS's
   internal extension list (`.ts`, `.tsx`, `.d.ts`, …). `.efx` is
   not in that list, so the configured project never contains the file.
2. **`getScriptKind` runs after project construction.** Overriding it to
   return `ScriptKind.TS` for `.efx` doesn't help — the file was already
   filtered out before any plugin hook can speak.
3. **Files opened in an editor under an unknown extension fall into an
   *inferred* project.** Inferred projects don't read
   `tsconfig.compilerOptions.plugins`. Our plugin never loads for that
   file.
4. **The inferred project uses default settings**, which type-check JSX
   against the React `JSX` namespace. Hence the diagnostics the user
   sees: real tsserver, but with no efx awareness whatsoever.

So Layer 1's interception is structurally invisible. We need to fix
the **file-attachment problem** before any plugin hook gets a chance.

This is the gap Vue's, Astro's, MDX's tooling fill via Volar. They use
a "virtual file" pattern: the editor sees `Counter.vue`, but tsserver
sees a virtual `Counter.vue.ts` whose content is compiled output.
URIs are translated bidirectionally for diagnostics, completions,
hover, go-to-definition, etc.

---

## 2. Approach

**One source-of-truth file (`.efx`) + one virtual file (`.efx.tsx`) per
source.** The plugin maintains the mapping, serves compiled content for
the virtual path, and rewrites URIs at the LSP boundary.

```
Disk           Editor sees           tsserver sees           Diagnostics flow
───────────────────────────────────────────────────────────────────────────
Counter.efx ─► Counter.efx (LSP) ─► Counter.efx.tsx (virtual) ─► remap URI+pos
                                                                back to .efx
```

The user doesn't notice the virtual file exists. tsserver thinks
`Counter.efx.tsx` is a regular `.tsx` file containing already-compiled
TypeScript (no JSX) — so type-checking works with our channel-fold
types, h.track rewrites, typed event handlers, all of it.

---

## 3. Architecture

### 3.1 Virtual file registry

A module-level map kept on the plugin instance:

```ts
interface VirtualFile {
  readonly sourcePath: string         // /…/Counter.efx
  readonly virtualPath: string        // /…/Counter.efx.tsx
  readonly source: string             // raw .efx contents
  readonly compiled: string           // transformEfx(source).code
  readonly mappings: SourceMapMappings // decoded source map
  readonly version: string            // monotonic; bumps on edits
}

const virtuals = new Map<string /* sourcePath */, VirtualFile>()
const sourceFromVirtual = new Map<string /* virtualPath */, string /* sourcePath */>()
```

### 3.2 LanguageServiceHost overrides

Beyond what Layer 1 already does, the plugin must:

| Method | Behavior |
|---|---|
| `getScriptFileNames()` | Return originals + virtual `.efx.tsx` for every known `.efx` in the project |
| `fileExists(p)` | If `p` ends in `.efx.tsx`, return `true` iff the source `.efx` exists. Else delegate. |
| `readFile(p)` | If virtual: return compiled content. Else delegate. |
| `getScriptSnapshot(p)` | If virtual: snapshot the compiled content. Else delegate. |
| `getScriptKind(p)` | If virtual: `ScriptKind.TSX`. |
| `getScriptVersion(p)` | If virtual: return the entry's `version` field. |

Critically — **do not** advertise the `.efx` path itself in
`getScriptFileNames`. Let it stay in the inferred project (which is
where Neovim's edits land), and keep the virtual `.efx.tsx` as the
file tsserver type-checks.

### 3.3 Edit synchronization (the hard part)

When Neovim sends `didChange` for `Counter.efx`:

1. tsserver applies the edit to the open `ScriptInfo` for `Counter.efx`.
2. The plugin observes the change (via `projectService` events or by
   polling `info.languageService.getProgram()` for stale virtual
   versions).
3. Re-run `transformEfx(newSource)` for the file.
4. Update `virtuals[sourcePath]`: new compiled, new mappings, bump
   version.
5. Notify tsserver that `Counter.efx.tsx` is dirty (via
   `host.getScriptVersion` returning the bumped version on the next
   read — tsserver checks versions per type-check pass).

The race: between (1) and (5), tsserver may run a type-check pass
using the *old* virtual content. The diagnostic comes back stale.
Mitigation: throttle/debounce edits before recompile; accept ≤1
keystroke of staleness; document.

### 3.4 Diagnostic boundary

Plugin wraps `getSemanticDiagnostics` / `getSyntacticDiagnostics` /
`getSuggestionDiagnostics`. For diagnostics referencing virtual files:

1. **Rewrite the SourceFile** so `d.file.fileName` is the source path,
   not the virtual one (Layer 1's existing code).
2. **Remap positions** via the source map (Layer 1's existing code).
3. **Substitute SourceFile.text** so the LSP `range` conversion
   (offset → line/col) uses source line starts (Layer 1's existing
   code).

That part of Layer 1 stays — it was always correct in isolation; what
was missing was the file ever reaching tsserver in the first place.

### 3.5 All other LS methods

To make completions / hover / go-to-def / find-references work,
**every** position-bearing response from the LS needs the same
translation: virtual file URI → source URI, virtual offset → source
offset.

This is where the LOC count balloons. tsserver's `LanguageService`
has ~40 position-returning methods. Each one needs:

- Input: if the call site is `getCompletionsAtPosition(sourcePath, pos)`,
  translate `(sourcePath, pos)` → `(virtualPath, virtualPos)` before
  delegating.
- Output: any `TextSpan` / `DocumentSpan` / `DefinitionInfo` etc. that
  contains a `fileName` and `textSpan` → translate back.

Volar handles this generically with a position-mapping framework. A
hand-rolled implementation would be ~500 LOC just for the wrappers.

## 4. Phasing

### Phase 1 — Virtual files for type-checking only *(target: ~200 LOC on top of Layer 1)*

- Implement §3.1 + §3.2.
- Wire `getScriptFileNames` to include virtual `.efx.tsx` for every
  `.efx` in the project root.
- No URI rewriting at the diagnostic boundary yet — diagnostics fire,
  but file URIs reference `Counter.efx.tsx`. Editor would show
  squiggles in the virtual file (which the user can't open).
- **Acceptance:** spawning tsserver against `apps/demo/`, requesting
  diagnostics for `Counter.efx.tsx` returns errors against
  *compiled* `Counter.efx` content (i.e., no JSX namespace errors,
  channel types visible).

### Phase 2 — Diagnostic URI rewriting *(~50 LOC)*

- Rewrite virtual URIs to source URIs in diagnostic responses (file
  + position via source map; SourceFile substitution).
- **Acceptance:** Neovim shows real efx-aware diagnostics in
  `Counter.efx` at correct lines.

### Phase 3 — Edit synchronization *(~100 LOC + careful testing)*

- §3.3: observe edits, recompile, version-bump.
- Debounce strategy: recompile at most every N ms; mark version
  stale eagerly so tsserver re-asks.
- **Acceptance:** live editing `.efx` shows updated diagnostics
  within ≤1 second; no stale-state corruption.

### Phase 4 — Completions / hover / go-to-def *(~300–500 LOC)*

- Wrap every position-bearing LS method.
- §3.5.
- **Acceptance:** hover on a JSX element in `Counter.efx` shows the
  correct h-call signature; completion inside `<Foo />` props
  surfaces TypedProps; go-to-def on `<UserPage />` jumps to its
  declaration in `.efx`.

### Phase 5 — Optional polish

- Hover that shows the *source* expression with its inferred Effect
  type, not the compiled form. Requires reverse position mapping
  + custom hover handlers.
- Refactorings (rename, organize imports) that respect virtual file
  boundary.
- Better handling of cross-file go-to-def when crossing `.efx` ↔
  `.ts`.

## 5. Alternative: adopt Volar directly

Volar 2 ships a framework specifically for this pattern. We'd write a
"language plugin" that defines:

- The file pattern (`*.efx`)
- The compile function (already have it: `transformEfx`)
- Virtual files (one TS-mode virtual per source)

Volar handles everything in §3.3–§3.5 generically. Estimated effort:
~300 LOC for the language plugin, plus accepting the dep weight of
`@volar/*` packages (~10 packages, ~5 MB installed). The Vue Vapor,
Astro, Vapor, MDX, etc. ecosystems use this path.

**Trade-off:** Volar buys us correctness + maintenance offload, costs
us framework alignment (everything goes through Volar's API instead
of `ts.server.PluginCreateInfo`) and dependency weight.

For a POC with a single editor target (Neovim), hand-rolled Phases
1–4 are probably equivalent effort to a clean Volar integration. For
broader editor support (VS Code extension, JetBrains, etc.), Volar's
ecosystem leverage starts to matter.

## 6. Risks

- **TypeScript's project-service hooks are mostly private.** A plugin
  can wrap the LanguageService and mutate the LanguageServiceHost,
  but it can't directly manipulate the ProjectService or change how
  files are routed to projects. The virtual-file trick works *only*
  because we let the source file stay in the inferred project and
  type-check the *virtual* file in the configured project — those
  are coupled only by the plugin's bookkeeping. Edge cases (project
  switch, tsconfig reload, file rename) need careful handling.
- **`extraFileExtensions`** is a TS 5+ feature that lets a project
  declare additional script-kind-mapped extensions. May reduce the
  virtual-file machinery if it works as we'd hope. Needs validation;
  not used in current sketch.
- **Position-map fidelity.** Our compiler does a lot inside JSX
  expressions (`.value` → `h.read`, identifier → `h.peek`,
  conditional `h.track` wrap, auto-injected imports). Edge cases
  where source positions don't have a clean mapping in the emitted
  output need a fallback (point at the nearest mapped position).
- **Performance.** Incremental compile on every keystroke could be
  hundreds of `transformEfx` calls per minute. Need to verify Babel
  is fast enough or add a deeper cache.

---

## 7. Decision point

Before committing to either path, validate **Phase 1 in isolation**:
write a small test that spawns `tsserver` as a subprocess, sends an
`open` request for `Counter.efx.tsx` (the virtual path), requests
diagnostics, and confirms they fire against compiled content. If
that works, the rest is mechanical (just laborious). If it doesn't —
because of some other tsserver invariant we missed — adopting Volar
is the right call.

The `tsserver` JSON-RPC harness for this kind of test is ~100 LOC
and probably worth writing first.
